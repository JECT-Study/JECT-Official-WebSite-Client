# JDS 컴포넌트 개발 하네스 사용 안내

이 하네스는 팀원이 짧게 요청해도 AI와 요구사항을 구체화하고, 구현과 검증까지 이어갈 수 있도록 도와줘요. Codex와 Claude Code가 저장소 안의 같은 스킬 원본을 읽어요. 개인 스킬 설치나 개인 폴더 연결 없이 사용할 수 있게 구성했어요.

## 필요한 안내를 찾아요

| 하고 싶은 일                                   | 읽을 곳                                                              |
| ---------------------------------------------- | -------------------------------------------------------------------- |
| AI에게 구현을 맡기거나 직접 구현할 준비를 해요 | [시작 방법](#이렇게-시작해요)                                        |
| 요구사항 초안과 질문 방식을 확인해요           | [조사·제안·질문](#ai가-먼저-조사하고-제안해요)                       |
| 구현과 검증의 세부 기준을 확인해요             | [구현·검증](#구현과-검증에서-챙기는-내용)                            |
| 리뷰나 답변 후 필요한 부분만 이어가요          | [부분 요청과 인계](#필요한-부분만-이어서-요청해요)                   |
| PR에 남길 합의사항을 정리해요                  | [PR 작성](#pr에는-명세-외-합의사항을-남겨요)                         |
| 파일 배치와 검증 결과를 확인해요               | [구성과 관리](#구성과-관리), [검증 결과](evals/evaluation-report.md) |

## 이렇게 시작해요

저장소를 열고 아래처럼 요청해 주세요. Figma 링크나 사용 화면을 알고 있다면 함께 알려 주세요. 모든 요구사항을 처음부터 작성할 필요는 없어요.

```text
JDS Select를 구현해줘.
Figma와 기존 코드를 먼저 확인하고 요구사항 초안을 보여줘.
중요한 결정이 빠져 있으면 추천안과 함께 질문해줘.
확정된 범위는 구현하고 FF·접근성·관련 동작까지 검증해줘.
```

직접 코드를 작성하려면 “코드는 내가 구현할게. 명세·API·시나리오를 먼저 정리하고, 구현 후 변경분을 검토해줘”라고 요청해 주세요. 리뷰만 요청하면 AI가 제품 코드를 수정하지 않아요.

스킬이 목록에 있으면 Codex의 `$ject-jds-workflow`, Claude Code의 `/ject-jds-workflow`로도 시작할 수 있어요. 보이지 않으면 새 세션에서 확인하거나 `.claude/skills/ject-jds-workflow/SKILL.md`를 읽고 적용하라고 알려 주세요. 지원 버전·프로젝트 신뢰·개인 설정에 따라 인식이 달라질 수 있어요.

## AI가 먼저 조사하고 제안해요

| 단계          | AI가 하는 일                                              | 사용자가 확인할 부분                 |
| ------------- | --------------------------------------------------------- | ------------------------------------ |
| 조사          | 현재 Figma·사용처·코드·규약을 읽어요                      | 찾을 수 없는 자료만 보충해요         |
| 요구사항 초안 | 확인된 사실·AI 제안·미결정을 구분해요                     | 목적·범위·해석이 맞는지 봐요         |
| 제안과 질문   | 더 작은 API·재사용·책임 분리와 빠진 동작을 안내해요       | 결과가 달라지는 중요한 결정을 답해요 |
| 구현          | 확정된 범위의 코드·타입·스토리·export·체인지셋을 작성해요 | 직접 구현한다면 이 단계를 맡아요     |
| 검증          | 변경에 맞는 FF·접근성·브라우저·패키지·저장소 검사를 해요  | 핵심 지적과 남은 검증을 봐요         |
| PR 설명       | 디자인 문서에 없는 실제 합의만 짧게 추려요                | 구현과 합의 내용이 일치하는지 봐요   |

충분한 명세가 있으면 추가 승인 없이 진행해요. 사용자 동작·공개 API·지원 범위가 달라지는 미결정은 선택지별 결과·추천·비용을 질문해요. 내부 파일 분리처럼 결과가 같은 선택은 기존 규약으로 판단해요. 추천이나 답변이 없다는 사실을 합의로 처리하지 않아요.

Select에는 단일·복수 선택·검색·해제, Dialog에는 닫힘·작성 중 내용·포커스, 날짜 입력에는 부분 입력·확정·제한·폼 계약 중 필요한 항목을 확인해요. 모든 항목을 모든 컴포넌트에 묻지 않아요. AI가 요청의 잘못된 전제나 더 단순한 방법을 발견하면 근거와 함께 설명해요.

## 구현과 검증에서 챙기는 내용

[상세 구현 절차](../../.claude/skills/ject-jds-workflow/references/implementation.md)에는 props·상태 소유권·이벤트 순서·외부 값 변경·폼 reset·Portal·수명·토큰·공개 계약이 있어요. 필요한 요구사항을 코드·스토리·검증 시나리오에 연결해요.

[FF 검토](../../.claude/skills/ject-jds-ff-review/SKILL.md)는 가독성·예측 가능성·응집도·결합도의 17개 항목을 관련 단위에 적용해요. 실제 변경 시나리오와 반증을 확인하고 불필요한 추상화를 피하도록 해요. 핵심 판단부터 보여주고 전체 범위표는 상세 기록에 남겨요.

[접근성 검토](../../.claude/skills/ject-jds-accessibility/SKILL.md)의 목표는 WCAG 2.2 A/AA예요. APG의 구현 권고와 구분하고, 관련 키보드·포커스·이름·상태·폼·시각 조건을 확인해요. 부분 검토가 제품의 공식 준수 선언을 뜻하지는 않아요.

검사는 [변경 내용에 따라 선택](../../.claude/skills/ject-jds-workflow/references/quality-gates.md)해요. 화면 영향이 없는 유틸·타입 변경은 브라우저 검사 제외 이유를 남길 수 있어요. 필요한데 도구가 없어 실행하지 못한 검사는 미검증이에요. 현재 AGENTS의 type-check/lint와 배포 코드 변경의 패키지·체인지셋 규칙은 지켜요.

Storybook 빌드·play assertion 실행·VRT 비교·자동 접근성·스크린 리더 낭독은 서로 다른 결과예요. 현재 checkout의 scripts·설정·도구부터 확인해요. 기존 도구로 가능한 범위를 마치고, 새 패키지·설정·CI가 필요하면 현재 승인 규칙을 따라요.

## 필요한 부분만 이어서 요청해요

```text
디자이너 답변은 “부분 입력을 유지한다”야.
결정과 관련된 구현·스토리·검증을 이어서 진행해줘.
```

```text
현재 변경분의 FF 품질을 검토해줘. 제품 코드는 수정하지 마.
```

```text
팝업이 열린 상태에서 disabled가 바뀌는 동작을 브라우저에서 확인해줘.
```

짧은 작업은 대화에 기록해요. 긴 작업이나 다른 도구로 넘길 때는 Git에서 제외되는 `.claude/jds-harness/_workspace/<작업명>/work.md` 하나를 사용해요. AI가 관리하므로 사용자가 JSON이나 역할 배정을 직접 작성할 필요는 없어요. 인계할 때는 이 파일의 절대 경로와 요청을 알려 주세요. 두 앱 사이에 자동 메시징을 설정한 구성은 아니에요.

## PR에는 명세 외 합의사항을 남겨요

AI는 현재 디자인 문서와 실제 질문·답변 기록을 비교해 문서에 없는 확정 결정만 짧게 정리해요. 동작·공개 API·지원 범위에 영향을 주는 내용을 한 문장씩 적고, 필요한 이유만 덧붙여요. AI의 단독 제안·미결정은 합의사항에 넣지 않아요. 항목이 없으면 생략해요.

기존 PR 템플릿의 변경 요약·검증 결과도 함께 작성해요. 자세한 기준과 가상 예시는 [PR 작성 규칙](../../.claude/skills/ject-jds-workflow/references/pull-request.md)에 있어요. PR 초안 작성과 실제 생성·게시·커밋·푸시는 요청한 권한을 따라요.

## 구성과 관리

원본은 `.claude/skills/ject-jds-*`에 있어요. `.agents/skills`는 같은 저장소 안의 상대 링크로 연결돼요. 기존 개인용 JDS·FF 스킬 6개를 프로젝트용 이름으로 옮겨 보완했으며, 개인 폴더와 자동 동기화하지 않아요. 같은 이름의 개인 스킬과 혼동하지 않도록 `ject-jds-*` 경로를 사용해요. 개인 원본은 수정하지 않았어요.

기본 대화의 메인이 조사·설계·구현을 맡고 필요한 경우 독립 FF·브라우저 검토를 호출해요. 모델은 부모 설정을 이어받아요. 자세한 [역할과 반환 계약](../../.claude/skills/ject-jds-workflow/references/roles.md)은 workflow 스킬에서 관리해요.

| 위치                              | 관리하는 내용                       |
| --------------------------------- | ----------------------------------- |
| `docs/ai/README.md`               | 동료가 읽는 시작 방법과 문서 탐색   |
| `.claude/skills/ject-jds-*`       | 공통 스킬 원본과 세부 실행 지침     |
| `.agents/skills/ject-jds-*`       | Codex가 같은 원본을 읽는 상대 링크  |
| `.claude/agents`, `.codex/agents` | 각 도구의 FF·브라우저 역할 진입점   |
| `scripts/ai`                      | 연결 검사기와 검사할 스킬·역할 목록 |
| `docs/ai/evals`                   | 행동·호출 경계 사례와 확인한 결과   |

코드 작성·체인지셋·타입·PR 규칙은 아래의 기존 문서를 그대로 사용해요. AI 안내에 같은 규칙을 복사해 따로 관리하지 않아요.

- [JDS 작업 지침](../../packages/jds/AGENTS.md): JDS의 파일 구조·compound·배럴·스타일·아이콘·스토리·VRT 베이스라인 규칙이에요. `packages/jds`에서 작업하면 Claude Code는 자동으로 읽고, Codex는 루트 AGENTS.md의 안내를 따라 읽어요.
- [체인지셋 작성 규약](../changeset-guide.md): 배포 코드 변경의 릴리스 안내를 작성할 때 읽어요.
- [타입 선언 규약](../type-convention.md): JDS 타입을 선언하거나 옮기기 전에 읽어요.
- [PR 템플릿](../../.github/PULL_REQUEST_TEMPLATE.md): 변경 요약과 검증 결과를 작성할 때 사용해요.

저장소 루트에서 다음 명령으로 경로·메타데이터·역할 연결을 확인할 수 있어요. Node.js 외의 추가 패키지는 설치하지 않아요.

```bash
node scripts/ai/check-harness.mjs
```

이 검사는 파일 연결과 제한된 메타데이터 형식을 확인해요. 앱의 실제 스킬 선택·권한이나 제품 품질 검증을 대신하지 않아요. 심볼릭 링크를 사용할 수 없는 환경에서는 canonical SKILL.md 경로를 직접 읽어 진행하고 링크 인식은 별도로 확인해 주세요.

팀원이 clone해 같은 원본을 읽을 수 있는 구조와 Figma·브라우저·보조 기술의 사용 권한은 별개예요. 계정·도구를 쓸 수 없다면 AI가 범위와 필요한 자료를 안내해요. 개인 실행 기록·설정·worktree는 PR 대상에서 제외해요.

## 문체와 개선

동료용 안내는 목적과 다음 행동을 먼저 설명하는 해요체로 작성해요. 실행 지침은 조건·행동이 명확한 지시형을 유지해요. 어느 쪽이든 조건·예외·검증 기준을 보존해요. 제품 문구는 Figma의 JDS Voice and tone 원칙을, 체인지셋은 별도 작성 규약을 우선해요.

[평가 사례](evals/behavior-cases.md)와 [검증 결과](evals/evaluation-report.md)에서 실제 확인 범위를 볼 수 있어요. 반복되는 문제는 근거와 함께 일반화해 기존 규칙을 보완해요. 사례마다 새 에이전트나 규칙을 쌓지 않아요.
