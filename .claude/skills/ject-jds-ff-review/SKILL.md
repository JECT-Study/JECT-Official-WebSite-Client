# FF 리뷰

[Frontend Fundamentals](https://frontend-fundamentals.com/code-quality/code/)는 좋은 프론트엔드 코드를 **변경하기 쉬운 코드**로 정의한다. 이 리뷰가 답해야 할 질문은 하나다.

> 새 요구사항이 왔을 때, 이 코드를 고치고 배포하기 수월한가?

판단 기준은 네 가지다. **가독성**(한 번에 고려할 맥락이 적고 위에서 아래로 읽히는가), **예측 가능성**(이름, 파라미터, 반환 값만 보고 동작을 알 수 있는가), **응집도**(함께 고쳐야 할 코드가 구조적으로 함께 고쳐지는가), **결합도**(고쳤을 때 영향 범위가 좁은가).

## 왜 느리게 하는가

이 리뷰는 일부러 느리다. 빠르게 하면 두 가지가 동시에 틀린다.

- **없는 문제를 만든다.** 숫자 리터럴마다 "매직 넘버", 삼항마다 "단순하게"를 붙이는 식의 패턴 대조는 지적 개수만 늘린다. FF는 오히려 중복을 허용하고 조건을 펼쳐 쓰라고 자주 말한다.
- **있는 문제를 놓친다.** 응집도와 결합도는 파일 하나만 봐서는 보이지 않는다. 사용처와 형제 코드를 읽고, 요구사항이 바뀌는 상황을 실제로 대입해 봐야 드러난다.

그래서 아래 순서를 건너뛰지 않는다. 범위 밖을 읽고, 항목을 하나씩 대입하고, 변경 시나리오를 돌리고, 지적마다 스스로 반박해 본 뒤, 무엇을 봤는지 기록한다.

## 0. 대상 정하기

리뷰 대상은 현재 사용자 요청의 경로·PR·브랜치다. 전달되지 않으면 현재 변경분을 확인한다.

- **비어 있음** — 현재 브랜치의 변경분. 프로젝트 문서가 정한 기준 브랜치(없으면 저장소 기본 브랜치)와의 merge-base 대비 diff에 더해, 커밋하지 않은 변경과 추적되지 않는 새 파일까지 포함한다. 새 파일을 빠뜨리기 쉬우니 `git status`로 확인한다.
- **경로** — 그 파일이나 디렉토리 전체.
- **숫자** — PR 번호. `gh pr diff`와 `gh pr view`로 읽는다.
- **브랜치 이름** — 기준 브랜치 대비 diff.

생성물, lock 파일, 스냅샷, 이미지, 벤더 코드는 뺀다. 스토리와 테스트는 사용 예시로 읽되 지적은 본 코드를 우선한다.

대상이 크면(대략 파일 15개나 1,500줄을 넘으면) 로직이 있는 파일부터 보고, 다 보지 못한 파일은 보고서의 "확인하지 못한 것"에 적는다. 본 척하지 않는다.

## 1. 맥락 읽기

지적을 시작하기 전에 읽는다.

1. **프로젝트 규약.** `AGENTS.md`, `CLAUDE.md`, 린트 설정, 기여 문서. 규약이 FF와 다르면 규약이 이긴다. 그 차이는 "의견"으로만 남긴다.
2. **변경 파일 전체.** diff 조각만 읽으면 단위의 역할을 알 수 없다. 파일을 처음부터 끝까지 읽는다.
3. **주변 코드.** 사용처(누가 import하고 무엇을 쓰는지), 같은 종류의 형제(같은 디렉토리의 다른 훅이나 유틸, 같은 접두어의 함수), 그리고 이름만으로 동작을 알 수 없는 import 대상.

3번이 없으면 이름 충돌, 반환 타입 일관성, 디렉토리 응집도, 연동된 값, 영향 범위, props drilling을 판단할 수 없다. 추측하지 말고 `rg`으로 확인한다.

## 2. 단위 목록 만들기

대상 코드를 리뷰 단위로 나눠 목록을 만든다. 컴포넌트, 훅, export된 함수, 열 줄 안팎을 넘는 내부 함수, 그리고 모듈 수준의 상수 맵이나 설정 객체가 각각 한 단위다. 이 목록이 다음 단계의 행이 된다.

## 3. 1차: 17개 항목 대입

**먼저 `references/criteria.md`를 끝까지 읽는다.** 항목마다 찾는 법, 지적하지 않는 경우, 고치는 방향이 있다. 아래 표는 요약일 뿐이다.

그다음 단위마다 17개 질문을 순서대로 던진다. 걸리는 곳은 줄 번호와 함께 후보로 적는다. 이 단계에서는 심각도를 정하지 않는다.

| ID  | 항목                                      | 묻는 질문                                                      |
| --- | ----------------------------------------- | -------------------------------------------------------------- |
| R1  | 같이 실행되지 않는 코드 분리하기          | 동시에 실행될 일이 없는 두 갈래가 한 단위에 섞여 있나          |
| R2  | 구현 상세 추상화하기                      | 이 단위의 역할 한 문장에 들어가지 않는 세부 절차가 펼쳐져 있나 |
| R3  | 로직 종류에 따라 합쳐진 함수 쪼개기       | 책임이 아니라 로직 종류로 묶여서 계속 불어날 구조인가          |
| R4  | 복잡한 조건에 이름 붙이기                 | 식을 다 풀어 읽어야만 조건의 뜻을 알 수 있나                   |
| R5  | 매직 넘버에 이름 붙이기                   | 이 값이 왜 이 값인지 작성자 말고도 알 수 있나                  |
| R6  | 시점 이동 줄이기                          | 동작 하나를 이해하려고 몇 번이나 다른 곳을 봐야 하나           |
| R7  | 삼항 연산자 단순하게 하기                 | 삼항이 중첩되거나 조건이 복합식인가                            |
| R8  | 왼쪽에서 오른쪽으로 읽히게 하기           | 범위 검사가 부등식 순서대로 읽히나                             |
| P1  | 이름 겹치지 않게 관리하기                 | 이름을 본 사람이 떠올릴 동작과 실제 동작이 같은가              |
| P2  | 같은 종류의 함수는 반환 타입 통일하기     | 형제 함수를 쓸 때마다 반환 타입을 확인해야 하나                |
| P3  | 숨은 로직 드러내기                        | 이름, 파라미터, 반환 타입에 없는 일이 안에서 벌어지나          |
| C1  | 함께 수정되는 파일을 같은 디렉토리에 두기 | 이 기능을 지울 때 폴더 하나만 지우면 끝나나                    |
| C2  | 매직 넘버 없애기                          | 이 값을 바꾸면 조용히 같이 바꿔야 하는 곳이 또 있나            |
| C3  | 폼의 응집도 생각하기                      | 검증 로직의 위치가 폼이 바뀌는 단위와 맞나                     |
| K1  | 책임을 하나씩 관리하기                    | 이걸 고치면 어디까지 다시 확인해야 하나                        |
| K2  | 중복 코드 허용하기                        | 이 공통화는 지금도 앞으로도 정말 같은 동작인가                 |
| K3  | Props Drilling 지우기                     | 값을 쓰지 않고 전달만 하는 컴포넌트가 있나                     |

React 코드가 아니거나 폼이 없으면 일부 항목은 해당 없음이다. 해당 없음도 판단이므로 이유와 함께 기록한다.

## 4. 변경 시나리오 대입

응집도와 결합도는 "바꿔 보기 전에는" 보이지 않는다. 의미 있는 단위마다 그 코드의 도메인에서 실제로 올 법한 요구사항 변경을 한두 개 정하고, 고쳐야 할 곳을 끝까지 따라간다.

쓸 만한 시나리오의 예는 다음과 같다. 필드나 옵션이 하나 늘어난다. 한도나 시간 값이 바뀐다. prop이나 필드 이름이 바뀐다. 사용처 한 곳만 다르게 동작해야 한다. 이 기능을 통째로 삭제한다.

시나리오마다 세 가지를 적는다.

- 고쳐야 하는 파일과 줄
- 함께 고쳐야 하는데 구조적으로 묶여 있지 않아 빠뜨릴 수 있는 곳 → 응집도 후보
- 이 변경과 상관없는 사용처까지 다시 확인해야 하는가 → 결합도 후보

## 5. 2차: 지적마다 반박해 보기

후보를 그대로 보고하지 않는다. 하나씩 다음 질문으로 반박을 시도하고, 살아남은 것만 남긴다.

1. **원문이 인정하는 예외인가.** `criteria.md`의 "지적하지 않는 경우"에 해당하면 버린다.
2. **프로젝트 규약이 지금 형태를 요구하는가.** 그렇다면 결함이 아니다.
3. **이번 변경이 만든 문제인가.** 원래 있던 코드라면 본 지적에서 빼고, 이번 변경에 실제로 영향을 줄 때만 따로 짧게 언급한다.
4. **제안대로 고치면 다른 기준이 나빠지는가.** 그렇다면 6단계의 상충 판단을 거친다.
5. **근거가 실제 코드인가.** 줄 번호를 다시 열어 확인한다. "아마 다른 곳에서도 쓸 것"처럼 확인하지 않은 전제가 있으면 확인하거나 버린다.

## 6. 상충 판단

네 기준을 한꺼번에 만족시키기는 어렵다. 공통화하면 응집도는 오르지만 한 번 추상화되어 가독성이 떨어지고, 중복을 허용하면 결합도는 내려가지만 한쪽만 고치는 실수가 생길 수 있다. 지적이 이 긴장 위에 있으면 무엇을 우선했는지 지적 안에 밝힌다.

- 함께 고치지 않으면 **오류가 나는** 코드라면 응집도를 우선해 공통화하거나 추상화한다.
- 그런 위험이 낮고 사용처마다 **갈라질 여지**가 있으면 가독성과 결합도를 우선해 중복을 허용한다.
- 추상화는 맥락을 줄이지만 시점 이동을 늘린다. **열어 보지 않아도 동작이 예측되는 이름**이면 추상화가 이득이고, 열어 봐야 한다면 펼치는 쪽이 낫다.
- 답이 미래 요구사항에 달려 있으면 결함으로 단정하지 않고 **질문**으로 쓴다.

## 7. 심각도

- **고쳐야 함** — 오해나 수정 누락이 실제 버그로 이어질 수 있는 것. 숨은 부수 효과, 같은 이름의 다른 동작, 섞인 반환 타입, 각각 하드코딩된 연동 값이 대표적이다.
- **고치면 좋음** — 읽거나 바꾸는 비용을 눈에 띄게 줄이는 것.
- **의견** — 상충이 있거나, 미래 요구사항에 달렸거나, 프로젝트 규약과 FF가 다른 것.

## 8. 보고

사용자의 언어로 쓴다. 동료에게 전달할 설명은 해요체로 작성하고 별도 문서 규약이 있으면 따른다. 지적이 많아도 독자가 먼저 읽을 것은 세 개 이하로 추린다. 꼼꼼함은 점검 과정과 범위표에 담고, 독자에게는 우선순위를 준다.

```markdown
# FF 리뷰: <대상>

**결론**: <이 코드가 변경하기 쉬운지에 대한 한두 문장 판단>

## 먼저 볼 것

우선 이 항목부터 확인해요.

1. `path:line` **[기준, 항목 이름]** <한 문장 요약>

## 전체 지적

### 가독성

- **[고쳐야 함 | 고치면 좋음 | 의견]** `path:line` 항목 이름 (ID)
  - 근거: <해당 코드 1~5줄 인용>, 그리고 읽는 사람이나 고치는 사람이 겪게 되는 일
  - 제안: <구체적인 변경. 필요하면 짧은 코드>
  - 상충: <있을 때만. 무엇을 우선했고 왜>

### 예측 가능성

### 응집도

### 결합도

<지적이 없는 기준은 "지적 없음" 한 줄>

## 대입한 변경 시나리오

- <시나리오> → <고쳐야 하는 곳> → <판단>

## 점검 범위표

| ID  | 항목                             | 결과                           | 무엇을 봤나 |
| --- | -------------------------------- | ------------------------------ | ----------- |
| R1  | 같이 실행되지 않는 코드 분리하기 | 지적 1 / 문제 없음 / 해당 없음 | <근거>      |

## 확인하지 못한 것

<읽지 못한 파일, 확인하지 못한 전제. 없으면 "없음">
```

범위표는 17행을 모두 채운다. "문제 없음"에는 **가장 의심스러웠던 지점과 넘어간 이유**를 적는다. 예를 들면 "가장 복잡한 조건은 `Input.tsx:42`의 2항 `&&`, 이름 없이도 읽힘". 이 칸을 채울 수 없다면 그 항목은 아직 확인하지 않은 것이다.

## 하지 않는 것

- **요청 없이 고치지 않는다.** 리뷰만 하고, 반영할지는 사용자가 정한다.
- **버그, 보안, 성능은 범위 밖이다.** 지나가다 본 것은 보고서 끝에 "범위 밖" 한 줄로만 남긴다.
- **포매터와 린터가 잡는 것은 지적하지 않는다.**
- **같은 원인을 두 번 보고하지 않는다.** R3과 K1, R5와 C2는 같은 냄새의 다른 면이다. 한 지적에 두 ID를 함께 단다.
- **반사적으로 추상화를 권하지 않는다.** "함수로 빼세요"가 먼저 떠오르면 6단계의 질문을 다시 본다.
