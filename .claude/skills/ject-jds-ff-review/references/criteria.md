## 읽는 법

항목마다 네 가지가 있다.

- **질문** — 이 항목이 사람의 말로 묻는 것
- **찾는 법** — 실제로 무엇을 읽고 무엇을 세는가. 여기 적힌 것을 하지 않고 "문제 없음"이라고 쓰지 않는다
- **지적하지 않는 경우** — 원문이 인정하는 예외와 과잉 지적을 막는 선
- **고치는 방향** — 제안할 때의 기본 형태

사람이 한 번에 머리에 올려 둘 수 있는 맥락은 예닐곱 개 정도다. 가독성 항목은 모두 이 한계를 넘기지 않도록 하는 방법이다.

## 가독성

### 맥락 줄이기

#### R1. 같이 실행되지 않는 코드 분리하기

- **질문**: 동시에 실행될 일이 없는 두 갈래가 한 컴포넌트나 함수에 섞여 있나?
- **찾는 법**
  1. 단위 안의 분기 조건을 전부 적는다.
  2. 같은 판별 값(`role`, `mode`, `variant`, `status`, `isEdit`, 플랫폼 등)이 두 곳 이상에서 반복되는지 본다. effect 안, 핸들러 안, JSX 안에 흩어진 경우가 전형적이다.
  3. 각 줄에 "A일 때만", "B일 때만", "공통"을 표시해 본다. A와 B가 번갈아 나타나면 후보다.
- **지적하지 않는 경우**: 분기가 한 곳뿐일 때. 두 갈래가 로직 대부분을 공유하고 한두 줄만 다를 때. 이 경우 나누면 중복이 더 커진다.
- **고치는 방향**: 맨 위에서 한 번만 분기하고 갈래별 컴포넌트나 함수로 나눈다. 각 갈래는 자기 경우만 안다.
- 원문: https://frontend-fundamentals.com/code-quality/code/examples/submit-button.html

#### R2. 구현 상세 추상화하기

- **질문**: 이 단위가 하는 일을 한 문장으로 말했을 때, 그 문장에 들어가지 않는 세부 절차가 본문에 펼쳐져 있나?
- **찾는 법**
  1. 단위의 역할을 한 문장으로 적는다.
  2. 본문을 블록으로 나누고, 그 문장과 직접 관련이 없는 블록을 찾는다. 로그인 확인 후 이동, 확인 다이얼로그 조립, 권한 검사 같은 것이 페이지 컴포넌트에 그대로 들어 있는 경우가 대표적이다.
  3. 읽는 사람이 동시에 기억해야 하는 것(상태, 파생 값, 핸들러, effect, 외부 훅)을 센다. 예닐곱 개를 넘으면 후보다.
  4. 핸들러 정의와 그것을 붙인 JSX 사이의 거리를 본다. 멀면 함께 고쳐야 할 둘이 떨어져 있는 것이라 응집도 문제도 겸한다.
- **지적하지 않는 경우**: 세부가 몇 줄이고 그 단위의 핵심일 때. 빼내면 읽는 사람이 꼭 알아야 하는 동작이 가려질 때(R6, P3과 부딪힌다).
- **고치는 방향**: Wrapper 컴포넌트나 HOC로 감싸거나, 트리거 UI와 그 로직을 함께 가진 전용 컴포넌트로 뺀다. 분리된 쪽의 로직이 원래 쪽을 참조하지 못하게 되는 것도 이득이다.
- 원문: https://frontend-fundamentals.com/code-quality/code/examples/login-start-page.html

#### R3. 로직 종류에 따라 합쳐진 함수 쪼개기

- **질문**: 이 훅이나 함수가 "무엇을 책임지는지"가 아니라 "어떤 종류의 로직인지"로 묶여 있나? 새 요구사항이 생기면 무심코 여기에 계속 얹게 되나?
- **찾는 법**
  1. 이름을 본다. `usePageState`, `useQueryParams`, `useModals`, `helpers`, `utils`, `manager`처럼 종류를 말하는 이름이면 의심한다.
  2. 반환 값을 본다. 서로 독립된 값과 세터가 한 묶음(`{ values, controls }` 등)으로 나오는가.
  3. 사용처를 `rg`해 각 사용처가 반환 값의 어느 조각을 쓰는지 적는다. 조각만 쓰는 사용처가 많으면 후보다.
  4. 한 조각이 바뀔 때 모든 사용처가 다시 렌더링되는 구조인지 본다.
- **지적하지 않는 경우**: 묶인 값들이 언제나 함께 읽히고 함께 바뀔 때. 한 폼의 상태나 시작일과 종료일 쌍이 그렇다.
- **고치는 방향**: 책임별로 나누고 이름을 구체적으로 붙인다. 이름이 구체적이어지는 것 자체가 개선의 신호다.
- K1과 같은 냄새의 다른 면이다. 지적은 하나로 묶는다.
- 원문: https://frontend-fundamentals.com/code-quality/code/examples/use-page-state-readability.html

### 이름 붙이기

#### R4. 복잡한 조건에 이름 붙이기

- **질문**: 이 조건이 무엇을 뜻하는지, 식을 다 풀어 읽어야만 알 수 있나?
- **찾는 법**: `if`, 삼항, `&&` 렌더링, `filter`/`some`/`every`/`find` 콜백의 조건식을 **전부** 훑는다. 다음 중 하나면 후보다.
  - 피연산자가 셋 이상이다
  - `&&`와 `||`가 섞여 있다
  - 부정이 겹쳐 있다
  - 콜백이 두 단 이상 중첩되어 있다
  - 식이 여러 줄에 걸친다
- **지적하지 않는 경우**: 단순하고 한 번만 쓰이는 조건(`x => x * 2`, `value == null`). 이름을 붙여도 식을 그대로 되풀이하는 이름밖에 나오지 않을 때.
- **이름을 붙일 가치가 있는 때**: 로직이 복잡할 때, 여러 곳에서 다시 쓸 때, 따로 단위 테스트하고 싶을 때.
- **고치는 방향**: 뜻이 드러나는 `is`, `has`, `can` 변수나 함수로 뺀다.
- 원문: https://frontend-fundamentals.com/code-quality/code/examples/condition-name.html

#### R5. 매직 넘버에 이름 붙이기

- **질문**: 이 값이 왜 이 값인지, 작성자가 아닌 사람도 알 수 있나?
- **찾는 법**: 숫자 리터럴을 **전부** 찾는다. 시간, 크기, 개수 제한, 상태 코드, 오프셋, 임계값이 대상이다. 같은 성격의 문자열(상태 값, 이벤트 이름)도 포함한다. 리터럴마다 "무슨 뜻이고 왜 이 값인가"에 코드만 보고 답할 수 있는지 확인한다.
- **지적하지 않는 경우**: `0`, `1`, `-1` 같은 자명한 산술이나 인덱스. 바로 옆의 이름이나 키가 뜻을 말해 줄 때(`padStart(2, "0")`, `{ length: 4 }`). 디자인 토큰을 써야 하는 스타일 값은 프로젝트 규약의 문제라 여기서 다루지 않는다.
- **고치는 방향**: 단위까지 드러나는 상수 이름을 붙인다(`ANIMATION_DELAY_MS`).
- 같은 값이 다른 곳과 함께 바뀌어야 한다면 C2로 올려서 본다.
- 원문: https://frontend-fundamentals.com/code-quality/code/examples/magic-number-readability.html

### 위에서 아래로 읽히게 하기

#### R6. 시점 이동 줄이기

- **질문**: 동작 하나를 이해하려고 몇 번이나 다른 곳으로 눈을 옮겨야 하나?
- **찾는 법**
  1. 단위에서 핵심 동작 하나를 고른다. 예를 들면 "이 버튼은 언제 비활성화되나".
  2. 그 답을 얻을 때까지 열어 봐야 하는 정의(함수, 상수 맵, 다른 파일)를 순서대로 적는다.
  3. 세 번 이상 옮겨야 하면 후보다. 조회 테이블, 그것을 해석하는 함수, 사용처로 쪼개 놓은 단순한 정책이 전형적이다.
- **지적하지 않는 경우**: 정책이 실제로 복잡해서(경우의 수가 많거나 여러 곳이 공유) 표로 빼는 편이 이득일 때. 옮겨 가야 하는 대상이 **열어 보지 않아도 동작이 예측되는** 잘 지은 이름의 함수일 때.
- **고치는 방향**: 조건을 요구사항 그대로 펼쳐 쓰거나, 매핑 객체를 사용하는 단위 안으로 가져와 한눈에 보이게 한다.
- R2와 긴장 관계다. 추상화는 맥락을 줄이지만 시점 이동을 늘린다.
- 원문: https://frontend-fundamentals.com/code-quality/code/examples/user-policy.html

#### R7. 삼항 연산자 단순하게 하기

- **질문**: 이 값이 어떤 조건에서 무엇이 되는지 한눈에 보이나?
- **찾는 법**: 삼항을 전부 찾는다. 두 단 이상 중첩되었거나, 조건부가 복합식이거나, 결과부에 또 분기가 있으면 후보다.
- **지적하지 않는 경우**: 한 단이고 조건이 단순하며 양쪽 값이 짧을 때.
- **고치는 방향**: `if`와 이른 반환으로 푼다. 값이 필요한 자리면 즉시 실행 함수나 별도 함수를 쓴다.
- 원문: https://frontend-fundamentals.com/code-quality/code/examples/ternary-operator.html

#### R8. 왼쪽에서 오른쪽으로 읽히게 하기

- **질문**: 범위 검사가 수학의 부등식(`min ≤ x ≤ max`)처럼 읽히나?
- **찾는 법**: 범위 검사를 전부 찾는다. `x >= min && x <= max`처럼 가운데 값이 양쪽에 따로 나오면 후보다.
- **지적하지 않는 경우**: 범위 검사가 아닌 서로 독립된 두 비교. 프로젝트 린트가 리터럴을 왼쪽에 두는 것을 금지할 때는 규약이 이기고, 차이만 의견으로 남긴다.
- **고치는 방향**: `min <= x && x <= max`.
- 원문: https://frontend-fundamentals.com/code-quality/code/examples/comparison-order.html

## 예측 가능성

#### P1. 이름 겹치지 않게 관리하기

- **질문**: 이 이름을 본 동료가 떠올릴 동작과 실제 동작이 같은가?
- **찾는 법**: 새로 만들었거나 바꾼 export 이름마다 세 가지를 확인한다.
  1. import한 라이브러리나 내장 API와 같은 이름인가.
  2. 저장소 안에 같은 이름의 다른 것이 있는가. `rg`으로 확인한다.
  3. 무언가를 감싸면서 원래 없던 동작(인증, 캐싱, 재시도, 변환)을 넣었는데 이름은 그대로인가.

  지역 변수가 바깥 이름을 가리는 섀도잉도 함께 본다.

- **지적하지 않는 경우**: 동작이 정말 같은 재export.
- **고치는 방향**: 더해진 동작이 드러나는 이름으로 바꾼다. 인증을 붙인 `get`이라면 `getWithAuth`.
- 원문: https://frontend-fundamentals.com/code-quality/code/examples/http.html

#### P2. 같은 종류의 함수는 반환 타입 통일하기

- **질문**: 같은 종류의 함수를 쓸 때마다 반환 타입을 확인해야 하나?
- **찾는 법**
  1. 대상 함수나 훅의 종류를 정한다. API 훅, 검증 함수, 파서, 포매터, 상태 훅 등.
  2. 같은 종류의 형제를 저장소에서 찾는다. 같은 디렉토리, 같은 접두어가 단서다.
  3. 반환 형태를 나란히 놓고 비교한다.

  `boolean`과 객체가 섞이는 경우를 특히 본다. 객체를 반환하는 검증 함수를 `if (check(x))`로 쓰면 항상 참이 된다.

- **지적하지 않는 경우**: 형제가 없을 때(해당 없음으로 기록). 종류가 실제로 다를 때.
- **고치는 방향**: 한 형태로 통일한다. 검증 결과는 `{ ok: true } | { ok: false; reason: string }` 같은 구별된 유니온이 좋다.
- 원문: https://frontend-fundamentals.com/code-quality/code/examples/use-user.html

#### P3. 숨은 로직 드러내기

- **질문**: 이름, 파라미터, 반환 타입만 보고는 알 수 없는 일이 안에서 벌어지나?
- **찾는 법**: 함수마다 시그니처에서 예상되는 일을 먼저 적는다. 그다음 본문에서 그 밖의 일을 찾는다.
  - 로깅, 분석 이벤트 전송
  - 페이지 이동
  - 스토리지나 쿠키 쓰기
  - 전역 상태 변경, 캐시 무효화
  - 토스트나 다이얼로그 띄우기
  - 인자로 받은 객체 변형
  - 포커스 이동

  `get`, `fetch`, `is`, `has`, `format`, `parse`, `to` 계열 이름인데 부수 효과가 있으면 강한 후보다. 컴포넌트라면 props에 드러나지 않는 전역 의존도 포함한다.

- **지적하지 않는 경우**: 이름이 그 효과를 말하고 있을 때. 그 효과가 그 훅의 존재 이유일 때.
- **고치는 방향**: 시그니처로 예측되는 일만 남기고, 나머지는 호출부로 올리거나 이름에 드러낸다. 숨은 로직이 실패하면 본래 기능까지 같이 깨진다는 점도 근거가 된다.
- 원문: https://frontend-fundamentals.com/code-quality/code/examples/hidden-logic.html

## 응집도

응집도는 "함께 고쳐야 할 코드가 반드시 함께 고쳐지도록 구조가 받쳐 주는가"다. 파일 하나만 읽어서는 판단할 수 없다.

#### C1. 함께 수정되는 파일을 같은 디렉토리에 두기

- **질문**: 이 기능을 지울 때 폴더 하나만 지우면 끝나나?
- **찾는 법**
  1. 추가하거나 옮긴 파일마다 누가 import하는지 `rg`한다.
  2. 한 기능이나 도메인에서만 쓰이는데 전역의 종류별 폴더(`hooks/`, `utils/`, `components/`, `constants/`)에 있으면 후보다.
  3. 다른 도메인 내부로 깊이 들어가는 상대 경로 import가 있는지 본다.
- **지적하지 않는 경우**: 실제로 여러 곳에서 쓰는 공용 코드. 프로젝트가 문서로 정한 구조를 따르고 있을 때. 뒤의 경우에는 규약과 FF가 다르다는 점만 의견으로 남긴다.
- **고치는 방향**: 그 기능의 디렉토리 아래로 옮긴다. 지금은 한 곳에서만 쓰이지만 공용 폴더에 둔 이유가 있다면 그 이유를 묻는다.
- 원문: https://frontend-fundamentals.com/code-quality/code/examples/code-directory.html

#### C2. 매직 넘버 없애기

- **질문**: 이 값을 바꾸면, 조용히 같이 바꿔야 하는 곳이 또 있나?
- **찾는 법**: R5에서 모은 리터럴마다 같은 값이나 연동된 값이 다른 곳에 있는지 `rg`한다. 자주 나오는 쌍은 다음과 같다.
  - JS의 대기 시간과 CSS의 애니메이션 시간
  - 검증 한도와 안내 문구 속 숫자
  - 페이지 크기와 그것을 전제한 계산
  - 정규식의 자릿수와 포맷 문자열, 문자열 위치 오프셋
  - 한 값에서 계산되어야 하는데 각각 하드코딩된 값
- **지적하지 않는 경우**: 우연히 값이 같을 뿐 의미가 다른 숫자. 이런 것을 하나의 상수로 묶으면 오히려 결합도가 생긴다.
- **고치는 방향**: 상수 하나로 선언하고, 연동된 값은 그 상수에서 계산한다.
- 한쪽만 고치면 조용히 깨지는 경우이므로 대개 "고쳐야 함"이다.
- 원문: https://frontend-fundamentals.com/code-quality/code/examples/magic-number-cohesion.html

#### C3. 폼의 응집도 생각하기

- **질문**: 이 폼은 필드 단위로 바뀌나, 폼 전체 단위로 바뀌나? 검증 로직의 위치가 그것과 맞나?
- **찾는 법**: 폼이 있을 때만 본다. 검증 로직이 어디에 있는지(필드 옆, 폼 스키마, 섞임)를 적고 아래와 맞춰 본다.
  - **필드 단위가 맞는 경우**: 필드마다 독립적이거나 비동기인 검증이 필요할 때(중복 확인 등), 필드와 검증을 다른 폼에서도 다시 쓸 때.
  - **폼 전체 단위가 맞는 경우**: 모든 필드가 하나의 기능을 이룰 때(결제, 배송), 단계별 입력일 때, 필드끼리 서로 참조할 때(비밀번호 확인, 합계).
  - 맞지 않게 놓였거나 한 폼 안에서 두 방식이 이유 없이 섞여 있으면 후보다.
- **지적하지 않는 경우**: 폼이 없는 코드(해당 없음). 단일 입력 컴포넌트 자체를 만드는 코드.
- **고치는 방향**: 변경이 일어나는 단위에 맞춰 검증을 옮긴다. 폼 전체 단위는 필드 간 결합이 높아져 재사용이 어려워진다는 대가를 함께 적는다.
- 원문: https://frontend-fundamentals.com/code-quality/code/examples/form-fields.html

## 결합도

결합도는 "고쳤을 때의 영향 범위"다. 사용처를 세지 않고는 판단할 수 없다.

#### K1. 책임을 하나씩 관리하기

- **질문**: 이걸 고치면 어디까지 다시 확인해야 하나?
- **찾는 법**
  1. 단위의 사용처를 `rg`으로 센다.
  2. 사용처마다 무엇을 쓰는지 적는다.
  3. 책임이 "이 페이지의 모든 무엇"처럼 넓고, 사용처들이 서로 다른 조각에 기대고 있으면 후보다.
- **지적하지 않는 경우**: 사용처가 하나뿐이고 늘어날 이유가 없을 때.
- **고치는 방향**: 책임별로 쪼개 수정의 영향 범위를 좁힌다.
- R3과 같은 냄새의 다른 면이다. 지적은 하나로 묶는다.
- 원문: https://frontend-fundamentals.com/code-quality/code/examples/use-page-state-coupling.html

#### K2. 중복 코드 허용하기

- **질문**: 이 공통화는 지금도, 앞으로도 정말 같은 동작인가?
- **찾는 법**: 세 방향을 모두 본다.
  1. **새로 만든 공통 코드**: 사용처가 몇 곳이고, 각 사용처의 요구사항이 갈라질 여지가 있는가. 열기와 로깅과 닫기처럼 여러 단계를 한데 묶었다면 그중 하나만 달라져도 인자가 늘어난다.
  2. **기존 공통 코드에 얹은 변경**: 옵션, 불리언 플래그, `variant` 분기가 늘었는가. 한 사용처의 특수한 요구를 받아 주려고 인자가 생겼다면 이미 갈라지고 있다는 신호다.
  3. **반대 방향**: 맞추지 않으면 오류가 나는 중복을 방치하고 있지 않은가. 이 경우는 응집도가 이긴다.
- **지적하지 않는 경우**: 동작과 모양이 같고 앞으로도 같을 것이 분명한 공통화.
- **판단 기준**: 함께 고치지 않으면 오류가 나면 공통화한다. 그렇지 않고 갈라질 여지가 있으면 중복을 허용한다.
- 미래 요구사항을 알 수 없으면 결함으로 쓰지 않고 질문으로 쓴다. 원문도 동료와 소통해 동작을 정확히 이해하라고 말한다.
- 원문: https://frontend-fundamentals.com/code-quality/code/examples/use-bottom-sheet.html

#### K3. Props Drilling 지우기

- **질문**: 이 prop의 이름을 바꾸면 몇 개의 컴포넌트를 고쳐야 하나? 그중 실제로 그 값을 쓰는 것은 몇 개인가?
- **찾는 법**: 컴포넌트의 prop마다 "사용"인지 "전달만"인지 표시한다. 전달만 하는 중간 컴포넌트가 있고 전달 깊이가 두 단 이상이면 후보다.
- **지적하지 않는 경우**: 그 prop이 중간 컴포넌트의 역할과 의도를 나타낼 때. 한 단만 내려 주는 평범한 전달.
- **고치는 방향**: 순서가 있다.
  1. `children` 조합으로 중간 단계를 없앤다.
  2. 조합으로 풀리지 않을 만큼 깊고 복잡할 때만 Context를 쓴다.

  Context부터 권하지 않는다. props는 컴포넌트가 무엇을 쓰는지 드러내는 수단이기도 하다.

- 원문: https://frontend-fundamentals.com/code-quality/code/examples/item-edit-modal.html
