# 질문과 역제안

## 어떤 결정이 필요한가

질문 전에 원문·관련 원칙·primitive·기존 사용처·이전 답변을 조사한다. 사용자 요청의 목적과 실제 결과를 확인하며 잘못된 전제도 근거로 설명한다. 현재 명세·코드에서 발견한 문제와 가능한 미래 확장을 구분한다.

| 분류                               | 처리                                                    |
| ---------------------------------- | ------------------------------------------------------- |
| 원문·요청에서 확정                 | 근거를 연결하고 구현·검증으로 진행                      |
| 가역적인 내부 기술 선택            | 기존 규약과 작은 변경으로 판단하고 필요할 때 이유 설명  |
| 사용자 동작·API·지원 범위의 미결정 | 선택지별 결과·비용·추천을 질문하고 의존 구현 대기       |
| 문서·동작·접근성 충돌              | 상충 근거와 측정·사용자 영향, 충돌을 해소할 대안을 제시 |

더 작은 API나 기존 컴포넌트 재사용, 브라우저 상태 활용, JDS/사용처의 책임 분리가 목적에 맞으면 먼저 제안한다. “공통화가 더 좋다” 같은 결론 대신 현재 사례와 바뀌는 책임을 설명한다. 사용자가 거절한 선택을 새 근거 없이 반복하지 않는다.

## 사용자에게 전달할 내용

한 질문은 한 결정에 집중한다. 우선순위가 높은 소수의 질문부터 하고 이미 조사로 답한 내용을 다시 묻지 않는다.

```text
확인한 내용과 출처:
아직 정해지지 않았거나 충돌하는 부분:
선택지 A / 선택지 B: 각각 화면·값·소비처에 나타날 결과와 비용
추천과 근거:
지금 결정할 질문:
답변 전 보류할 동작 / 계속 가능한 작업:
```

예: 날짜 일부를 입력한 뒤 바깥을 누르는 정책이 없다면, 입력 내용을 유지하는 안과 마지막 확정값으로 돌아가는 안의 결과를 설명한다. 실제 사용 장면과 원문에 근거해 추천하되 추천 자체를 정답으로 기록하지 않는다.

예: hover/focus prop 추가 요청에는 브라우저 상태로 해결 가능한지 조사하고, 외부 강제 제어 사례가 있는지 확인한다. 이미 충분한 동작 명세라면 불필요한 설문이나 승인 대기를 추가하지 않는다.

사용 가능한 사용자 입력 도구로 질문한다. 도구가 없으면 대화에 질문을 남긴다. 디자이너에게 전달할 문구 작성과 실제 메시지·Figma 댓글 전송은 별도 행동이다. 전송은 명시적으로 허용된 범위에서만 한다.

## 답변 이후

실제 답변·출처·채택한 결정·적용 범위를 작업 기록에 남긴다. 계약·API·상태 전이·스토리·검증을 함께 갱신한다. 현재 디자인 문서에 없는 확정 결정만 PR 합의사항 후보로 표시한다. 뒤에 디자인 문서가 갱신되면 PR 작성 시 중복 여부를 다시 확인한다.

침묵·추천·시간 경과로 질문을 답변 완료로 바꾸지 않는다. 사용자가 명시적으로 임시 가정을 승인하면 그 범위와 이후 변경 비용을 남긴다. 새 결정이 범위를 넓히면 영향과 대안을 설명하고 현재 권한을 따른다.
