# JDS 요구사항 조사와 핸드오프

## 먼저 조사한다

요청, Figma 노드, 기존 코드와 사용처를 먼저 읽는다. Figma 파일 위치는 [탐색 지도](references/jds-design-map.md)에서 찾되, 지도의 내용을 최신 요구사항으로 믿지 않는다.

Figma에 접근할 수 없으면 받은 자료와 코드에서 확인되는 사실만 모으고, 필요한 자료를 질문한다. 지금 코드의 동작을 디자인 의도나 공식 지원 범위로 확정하지 않는다.

Figma 도구를 쓸 때는 그 도구가 요구하는 스킬을 먼저 읽는다. `get_design_context`는 design-to-code, `use_figma`는 figma-use 스킬이다. 조회만 하고, 디자인을 만들거나 고치거나 댓글을 달지 않는다.

Figma는 페이지 개요, 관련 원칙과 Foundation, 대상 컴포넌트와 variant, 필요한 인스턴스 순으로 좁혀 읽는다. 레이어 구조나 생성 코드만 보고 HTML 의미나 공개 props를 정하지 않는다.

## 요구사항 초안을 보여준다

[계약 템플릿](../ject-jds-workflow/assets/component-contract.md)에서 해당하는 행만 골라 세 가지로 나눠 보여준다.

- 확인된 요구사항과 그 출처
- AI의 제안과 이유, 비용
- 정해지지 않은 것과 그 영향

사용 장면, JDS와 소비처의 책임, 가장 작은 사용 예시를 먼저 정리한다. 요구사항이 충분하면 짧게 공유하고 바로 진행한다. 문서 전체의 승인을 따로 받지 않는다.

명세에 없을 때 확인할 결정은 컴포넌트 종류마다 다르다.

| 대상              | 명세에 없을 때 확인할 결정                                      |
| ----------------- | --------------------------------------------------------------- |
| Button, Link      | 동작인지 이동인지, 로딩 중 조작, 아이콘만 있는 사용             |
| Select 등 선택    | 단일 선택과 복수 선택, 검색과 해제, 빈 목록, 검색 요청의 소유권 |
| Dialog, Popover   | 닫힘과 확정과 취소, 작성 중이던 내용, 열 때와 닫을 때의 포커스  |
| 날짜, 텍스트 입력 | 값 형식, 부분 입력과 확정, 외부 값 거절, 제한, 제출, reset      |
| 표시 컴포넌트     | 정보인지 장식인지, 긴 콘텐츠와 빈 콘텐츠, 테마, 화면 크기 변화  |

모든 항목을 모든 컴포넌트에 묻지 않는다. 가능한 옵션을 모두 공개 API로 만들지 않는다. 키보드, 레이블, 포커스 같은 접근성은 기본 품질로 적용하고 "접근성이 필요한가"를 묻지 않는다. 확정된 기준과 충돌하는 디자인에는 측정값과 근거, 지킬 수 있는 대안을 함께 제시한다.

## 제안하고 질문한다

[질문과 역제안 절차](references/questions.md)를 따른다. 기존 컴포넌트 재사용, 브라우저가 맡는 상태, 소비처 정책 분리, 더 작은 API로 요구를 만족할 수 있으면 근거와 트레이드오프를 들어 먼저 제안한다.

사용자에게 보이는 결과나 공개 계약이 달라지는 결정, 의도가 충돌하는 부분은 사용자에게 묻는다. 내부 파일 분리처럼 결과가 같고 쉽게 되돌릴 수 있는 선택은 기존 규칙으로 정한다.

답변에 의존하는 구현만 보류하고 나머지는 계속한다. 받은 답변은 출처와 적용 범위를 함께 작업 기록에 남기고, 계약과 스토리와 검증에 반영한다. 원문에 없던 확정 결정은 PR의 명세 외 합의사항 후보가 된다. 추정이나 추천은 합의가 아니다.
