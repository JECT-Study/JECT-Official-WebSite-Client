# JDS 요구사항 조사와 핸드오프

## 먼저 조사

현재 요청·Figma 파일과 노드·조회 시점·기존 코드와 사용처를 확인한다. 기본 파일 위치는 [탐색 지도](references/jds-design-map.md)에서 찾되 최신 요구사항으로 믿지 않는다. Figma가 없거나 접근하지 못하면 제공 자료와 코드에서 확인 가능한 사실을 모으고, 필요한 자료나 실제 사용자 결과를 질문한다. 현재 동작을 새 디자인 의도나 공식 지원 범위로 확정하지 않는다.

실제 Figma 도구를 사용할 때 제공되는 필수 스킬을 먼저 읽는다. get_design_context는 design-to-code, use_figma는 figma-use를 따른다. 그런 스킬·도구가 없으면 사용할 수 있다고 가정하지 않는다. 조회를 디자인 생성·수정·댓글 게시로 확대하지 않는다.

페이지 개요 → 관련 원칙·Foundation → 대상 문서·component set·variant → 필요한 인스턴스 순으로 좁힌다. 메타데이터·생성 코드·레이어 구조만으로 원문 의도·HTML 의미·공개 props를 결정하지 않는다.

## 요구사항 초안

[계약 템플릿](../ject-jds-workflow/assets/component-contract.md)의 관련 행을 사용해 확인된 요구사항(출처), AI 제안(이유·비용), 미결정(영향)을 구분한다. 사용 장면·JDS/소비처 책임·가장 작은 사용 예시를 먼저 정리한다. 충분한 요구사항은 짧게 공유하고 진행하며 전체 문서 승인을 추가로 요구하지 않는다.

| 대상             | 명세에 없을 때 확인할 결정                             |
| ---------------- | ------------------------------------------------------ |
| Button/Link      | 수행 동작·이동 의미, 로딩 중 조작, 아이콘만 있는 사용  |
| Select/복합 선택 | 단일·복수 선택, 검색·해제, 빈 목록, 검색 요청의 소유권 |
| Dialog/Popover   | 닫힘·확정·취소, 작성 중 내용, 진입·복귀 포커스         |
| 날짜·텍스트 입력 | 값 형식·부분 입력·확정, 외부 값 거절, 제한·제출·reset  |
| 표시 컴포넌트    | 정보·장식 의미, 긴 콘텐츠·빈 콘텐츠·theme·화면 변화    |

전 항목을 모든 컴포넌트에 묻지 않는다. 기술적으로 가능한 모든 옵션을 공개 API로 늘리지 않는다. 키보드·레이블·포커스 등 관련 접근성은 기본 품질 기준으로 적용하고 “접근성이 필요한가”로 선택시키지 않는다. 확정 기준과 충돌하는 디자인은 측정·근거·준수 가능한 대안을 제시한다.

## 제안과 질문

[질문·역제안 절차](references/questions.md)를 따른다. 기존 재사용·브라우저 상태·소비처 정책 분리·더 작은 API가 요구를 만족하면 근거와 트레이드오프를 제안한다. 실제 사용자 결과·공개 계약이 달라지거나 의도가 충돌하면 사용자에게 확인한다. 내부 파일 분리 등 결과가 같고 쉽게 되돌릴 선택은 기존 규칙으로 결정한다.

답변에 의존하는 구현만 보류한다. 실제 답변과 출처·적용 범위를 작업 기록에 남기고 계약·스토리·검증을 갱신한다. 원문에 없는 확정 결정은 PR 작성 시 합의사항 후보가 된다. 추정이나 추천은 합의가 아니다.

## 테스트 시나리오

- 짧은 Select 요청 → 자료를 먼저 읽고 빠진 중요한 선택만 질문. 추천은 확인한 사용 장면과 연결.
- Button의 isFocused prop 요청 → 브라우저 상태로 충분한지 조사·역제안하고 외부 강제 사용 사례 확인.
- 명세 충돌 또는 접근 불가 → 확인한 사실·대안·보류 범위 표시. 현재 코드로 의도를 만들어내지 않음.
