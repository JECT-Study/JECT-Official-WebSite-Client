# JDS 컴포넌트 설계

먼저 `ject-jds-context`로 현재 저장소와 변경 범위를 확인한다. 디자이너의 명세를 구현하며 시각적 디자인을 임의로 재설계하지 않는다. 입력이 부족하면 기존 코드와 명세에서 확인 가능한 부분부터 진행한다.

## 설계 순서

1. 소비처 사용 예시, 명세의 상태/variant, 컴포넌트가 보장할 행동과 소비처 책임을 정한다.
2. native 요소와 기존 Radix/JDS primitive를 확인한다. `Field`, `Listbox`, 공통 state/focus 훅이 이미 맡은 책임을 중복 구현하지 않는다.
3. [상태·이벤트 계약](references/state-contracts.md)을 필요한 범위에서 적용한다. 외부 값 변경뿐 아니라 소비처가 변경을 거절하는 경우도 설명한다.
4. 단일 컴포넌트, compound, hook, slot 중 가장 작은 충분한 API를 고른다. 조합을 통제할 이유가 있을 때 context를 사용한다. 네이티브 boolean과 독립적인 상태 flag는 유지할 수 있다.
5. 대표 형제 컴포넌트와 실제 소비처를 비교해 반복되는 규칙과 예외를 구분한다. props 타입을 바꾸기 전 타입 규약을 읽고 공개 배럴·ref·event·DOM 영향도 확인한다.
6. 키보드·포커스·폼 계약은 `ject-jds-accessibility`로 검증한다. 성능은 증거가 있을 때만 최적화한다. React 18 지원 범위와 최신 문서의 버전 차이를 확인한다.

## 결과와 구현 범위

제안 API와 짧은 사용 예시, 상태 소유권, 사용자 조작 결과, 기존 방식과의 트레이드오프, 호환성 및 검증 방법을 제시한다. 요청이 설계라면 구현하거나 의존성을 설치하지 않는다. 구현이 요청되면 해당 책임의 파일만 수정하고 현재 저장소의 스토리·체인지셋·검증 규칙을 적용한다.

전체 아키텍처 검토를 요청받으면 source → primitive → public component → story/test → 소비처를 대표 사례로 추적한다. 폴더 수나 컴포넌트 수로 성숙도를 평가하지 않는다.
