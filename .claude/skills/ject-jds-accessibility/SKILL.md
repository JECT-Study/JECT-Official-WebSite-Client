# JDS 접근성 구현과 검증

이 하네스의 접근성 검토 목표는 WCAG 2.2 A/AA다. 부분 검토를 제품의 공식 준수 선언으로 표현하지 않는다. AAA 개선과 APG 권고를 AA 필수 조건과 구분한다.

1. `ject-jds-context`와 실제 native/primitive 구현을 읽고 사용자 조작, 컨트롤 역할, 상태를 파악한다.
2. [W3C 기준](references/w3c-baseline.md)에서 해당 성공 기준과 APG 패턴을 선택한다. native HTML을 우선하고 필요 없는 role/live region은 추가하지 않는다.
3. [검증 절차](references/verification.md)에 따라 이름·설명·폼, 키보드 행렬, 포커스, 표시/ARIA 상태, 시각적 접근성의 해당 경로를 점검한다.
4. 정적 코드, 실제 렌더 DOM/접근성 트리, 브라우저 조작, 보조 기술의 증거를 구분한다. Radix가 제공하는 동작도 wrapper가 보존하는지 확인한다.
5. 자동 도구가 이미 설정되어 있는지 확인하고 실행한다. 새 도구가 필요하면 프로젝트 적합성과 변경 범위를 제시하며 설치·설정·CI 변경은 승인 범위를 따른다.

## 기록

각 지적은 코드 위치, 입력 방법/상태, 재현, 실제·기대 결과, 영향, 성공 기준 번호·수준 또는 APG 링크, 검증 방법을 갖춘다. 확정 결함, 추정 위험, 권고, 미검증을 분리한다. 스크린 리더를 실행하지 않았다면 낭독 결과를 단정하지 않는다.

비대화형 접근성 측정은 화면을 변경하지 않는 DOM/스타일 조회로 충분할 수 있다. 사용자가 직접 확인할 때만 브라우저를 띄워 해당 화면을 남긴다. 코드 리뷰 요청을 수정이나 PR 댓글 게시로 확대하지 않는다.
