# JDS 컴포넌트 개발

사용자의 최신 요청과 현재 AGENTS.md를 따른다. 구현·설계 지원·리뷰·부분 재실행 중 요청한 범위만 수행한다. 별도 실행 엔진을 가정하지 않고 실제로 제공되는 도구를 사용한다. 하네스의 검토 목표를 제품 품질 인증으로 표현하지 않는다.

## 0. 대상과 작업 방식

[저장소 맥락](../ject-jds-context/SKILL.md)을 한 번 확인한다. git root·branch·HEAD·dirty 파일과 대상 PR의 base/head, 소유 파일, 실행 가능한 도구를 확인한다. 같은 작업에서 확인한 자료는 재사용한다. 개인 스킬을 이름만으로 호출하지 말고 이 저장소의 링크된 SKILL.md를 읽는다.

- 구현 요청은 확정된 범위의 코드·스토리·검증까지 진행한다.
- 사용자가 직접 구현하면 명세·API·시나리오를 지원하고 구현 완료 후 요청된 검토를 한다.
- 리뷰 전용은 수정·게시하지 않는다. 기능 결함만 확인하면 [코드 리뷰](../ject-jds-review/SKILL.md)의 관련 범위만 적용한다.
- 단순 탐색·문서·체인지셋만 요청하면 그 범위의 현재 규약을 적용한다. 전체 설계와 제품 검증으로 확대하지 않는다.

## 1. 요구사항을 함께 구체화

요청이 짧아도 즉시 기능을 추측해 구현하거나 긴 설문부터 보내지 않는다. [명세 조사·제안·질문](../ject-jds-figma-handoff/SKILL.md)을 적용해 현재 Figma, 사용처와 코드를 먼저 읽는다. Figma 연결이 없으면 제공 자료와 현재 코드에서 확인 가능한 범위를 조사하고, 디자인 의도와 일치 여부는 미확정으로 둔다.

[구현 계약](assets/component-contract.md)의 관련 항목만 사용해 **확인된 요구사항 / AI의 구현 제안 / 결정이 필요한 내용**을 출처와 함께 짧게 제시한다. 충분한 명세가 있으면 추가 승인 절차 없이 진행한다. 버튼에 복합 입력의 모든 항목을 강제하지 않는다.

기존 컴포넌트 재사용, 더 작은 API, 브라우저가 맡을 상태, JDS와 소비처의 책임 경계, 빠진 상태·검증을 근거가 있을 때 선제적으로 제안한다. 사용자의 전제를 그대로 긍정하지 않고 목적·대안·비용을 비교한다. 가상의 확장 요구로 새 기능·추상화를 늘리지 않는다.

사용자 동작·공개 API·디자인 의도·지원 범위가 달라지는 미결정은 근거·선택지·추천·화면 결과를 묶어 우선순위가 높은 질문부터 한다. 가역적인 내부 구현 선택은 기존 규약으로 판단한다. 답변에 의존하는 변경만 기다리고 독립 작업은 계속한다. 추천·침묵·시간 경과는 합의가 아니다. 답변의 실제 출처와 적용 범위를 남긴다.

## 2. 설계와 구현

[컴포넌트 설계](../ject-jds-component-design/SKILL.md)와 [상세 구현 절차](references/implementation.md)를 적용한다. 요구사항을 API·상태 전이·스토리·검증 시나리오에 연결한다. 기존 소비처 동작과 타입·DOM·ref·폼 계약을 확인한다. 토큰 변경에는 [토큰 스킬](../ject-jds-tokens/SKILL.md)을 읽는다.

코드·스토리·타입·공개 배럴을 함께 갱신한다. 배포 코드 변경에는 현재 체인지셋 규약을 읽고 변경 안내를 작성한다. 요청 밖 공통 primitive·토큰·의존성·설정 변경이 필요하면 영향과 대안을 먼저 제시하고 현재 권한을 따른다.

## 3. 변경에 맞는 검증

[검증 선택과 판정](references/quality-gates.md)으로 필요한 검사와 제외 이유를 정한다. 접근성은 [접근성 기준](../ject-jds-accessibility/SKILL.md)과 [브라우저 실행](../ject-jds-browser-check/SKILL.md)을 적용한다. 배포 코드·공개 계약 변경은 [패키지 검사](../ject-jds-package-check/SKILL.md)를 연결한다.

코드 품질의 FF 17개 항목 전수 검토는 메인이 직접 하지 않고 `ject-jds-ff` 역할에 맡긴다. 메인은 FF 스킬을 읽지 않고, 반환된 핵심 지적을 반영할지 판단한다. 역할을 쓸 수 없는 도구에서만 메인이 [FF 검토](../ject-jds-ff-review/SKILL.md)를 직접 적용하고 그 사실을 보고한다.

나머지는 메인의 순차 실행이 기본이다. 복합 상태·폼·Portal·포커스 변경에는 도구가 있으면 `ject-jds-browser`도 사용한다. [역할과 반환 계약](references/roles.md)을 따르고 동시 실행은 기본 메인 포함 3명 이내다. 구현자의 결론 대신 원자료·요구사항·대상 코드를 전달한다. 같은 파일을 동시에 편집하지 않는다. 독립 검토가 불가능하면 메인이 확인하고 그 한계를 보고한다.

## 4. 기록·재개·PR

[작업 기록](references/record-contract.md)은 짧은 작업에서는 대화, 장기 작업·질문 대기·도구 간 인계에서는 Markdown 하나를 사용한다. 별도 JSON 완료 판정이나 증거 해시 입력을 요구하지 않는다. 재개할 때 현재 HEAD와 dirty diff를 비교하고 영향받은 판단·검증만 갱신한다. 파일 검사가 실제 관찰·FF·접근성 판정을 대신하지 않는다.

PR 설명 작성 요청에는 [PR 작성](references/pull-request.md)을 적용한다. 리뷰어가 PR만 읽고 무엇을, 왜, 어디를 볼지 알 수 있게 짧게 쓴다. 명세 외 합의사항은 현재 디자인 문서에 없고 실제 함께 확정한 결정만 짧게 추린다. 원문·제안·미결정을 합의로 바꾸지 않는다. 설명 초안 작성과 커밋·푸시·PR 생성·댓글 게시 권한을 구분하고 이미 주어진 권한은 반복 확인하지 않는다.

최종 보고는 결과·소비처 영향·핵심 지적·실제 검사·열린 질문과 미검증을 먼저 설명한다. FF 전체 근거는 보존하되 우선 읽을 핵심은 세 가지 이하로 추린다. 다음 단계는 현재 요청과 도구로 가능한 일은 수행하고, 사용자 결정이 필요한 부분과 직접 구현 시 이어서 요청할 작업만 안내한다.

동료가 읽는 안내·질문·결과 보고·PR 설명은 [문체 기준](../../../docs/ai/README.md#문체와-개선)에 따라 해요체로 작성한다. 조건·예외·검증 기준과 문서별 별도 규약은 보존한다.

## 테스트 시나리오

- “Select 만들어줘” → 현재 자료 조사 → 요구사항 초안 → 사용자 결과가 다른 미결정 질문과 근거 있는 역제안 → 확정 범위 구현.
- 완전한 Button 명세 → 짧은 확인과 구현. 불필요한 확인 대기나 compound·Context 확대 없음.
- 부분 입력 정책 답변 도착 → 실제 결정과 관련 API·스토리 갱신 → 영향받은 검증 재실행 → PR 합의사항 후보 정리.
- 문서만 변경 또는 브라우저 도구 부재 → 필요한 범위·미검증 구분. 품질 통과나 실행 결과를 만들어내지 않음.
- 행동·호출 경계 평가는 [평가 사례](../../../docs/ai/evals/behavior-cases.md)를 따른다.
