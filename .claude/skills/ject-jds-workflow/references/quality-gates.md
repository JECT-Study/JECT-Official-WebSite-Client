# 검증 선택과 판정

작업을 시작할 때 변경의 책임·공개 계약·위험에 맞는 검사를 선택한다. 적용되지 않는 검사의 제외 이유와 필요한 검사를 실행하지 못한 상태를 구분한다. 실패나 도구 부재를 이유로 원래 필요한 검사를 제외하지 않는다.

| 변경                  | 필요한 범위                                                                                      |
| --------------------- | ------------------------------------------------------------------------------------------------ |
| 새 컴포넌트           | 요구사항·API·상태, 관련 코드 FF, 해당 접근성·동작·시각, 패키지와 저장소 검사                     |
| 로직·이벤트·폼·포커스 | 영향받은 코드의 FF·상태 전이·회귀, 사용자 동작이 바뀌는 브라우저·접근성 경로                     |
| 스타일·토큰           | 관련 렌더/스타일 코드 FF, 영향받은 theme·state·콘텐츠·viewport·시각·접근성                       |
| 내부 유틸·타입        | 관련 코드 FF·값/타입 계약·사용처 영향. 화면·동작 영향이 없으면 브라우저 제외 이유 기록           |
| 스토리·문서만         | 변경 자료·링크·관련 스토리 확인. 제품 전체 FF·브라우저·패키지 빌드·체인지셋을 자동 강제하지 않음 |
| 버그만 확인하는 리뷰  | 요청된 결함과 재현 경로. FF 전수 평가는 명시 요청·종합 품질 검토일 때 적용                       |

현재 AGENTS의 type-check/lint는 변경 종류와 별개로 지킨다. 배포 코드 변경은 패키지 빌드와 현재 규약의 체인지셋을 연결한다. ESM/CJS·Next/RSC 등 특정 소비 환경의 지원을 바꾸거나 주장하면 해당 환경에서 실행한다.

## FF와 접근성의 기준

FF 전수 검토는 `ject-jds-ff` 역할이 [FF 스킬](../../ject-jds-ff-review/SKILL.md)로 수행한다([역할과 반환 계약](roles.md)). 메인은 검토 대상 범위와 요구사항을 넘기고, 돌아온 핵심 지적과 미확인 범위를 결과 보고에 옮긴다. 코드 길이·숫자·props 전달만으로 기계적으로 추상화하지 않는다.

접근성 기준과 예외는 [접근성 스킬](../../ject-jds-accessibility/SKILL.md)의 W3C 기준·검증 절차를 단일 참고로 읽는다. 하네스 목표는 WCAG 2.2 A/AA이며 APG 권고와 구분한다. 기준 수치를 다른 문서에 복제하거나 AA·AAA를 섞지 않는다. 실제 브라우저·보조 기술·자동 검사 증거를 구분한다.

## 결과와 완료 범위

- 통과: 실제 수행한 검사에서 기대 결과를 확인한 근거가 있다.
- 결함: 재현 조건·기대/실제 결과·코드/관찰 근거와 영향이 있다. 기능·FF·접근성·디자인을 구분한다.
- 제외: 변경의 영향상 적용되지 않으며 이유가 있다. 필요한 검사의 도구 부재와 다르다.
- 미검증/실패/캐시: 각각 실제 상태를 기록한다. 캐시 결과가 현재 대상에 유효한지도 확인한다.

결과 보고에는 구현 범위와 검증 완료 범위를 함께 쓴다. 필요한 질문이나 필수 검사가 남으면 전체 완료를 주장하지 않는다. 사용자가 범위를 명시적으로 줄이면 새 범위와 남은 위험을 설명하며 이전 실패를 통과로 바꾸지 않는다.

Storybook 빌드, play 코드, 실제 play assertion 통과, VRT 비교, 스크린 리더 낭독은 서로 대체하지 않는다. VRT baseline 생성은 비교 통과가 아니다. 환경 한계는 가능한 검증을 마친 뒤 필요한 다음 작업과 함께 기록한다.
