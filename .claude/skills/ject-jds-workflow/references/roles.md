# JDS 하네스의 역할과 반환 계약

## 메인과 위임 범위

기본 대화의 메인이 요구사항 조사·제안·질문·설계·구현·검증 선택과 결과 통합을 맡는다. 토큰과 패키지 검사는 필요한 전문 스킬을 읽고 수행한다. 별도 역할을 매번 모두 실행하지 않는다.

FF 전수 검토는 코드 변경이 있는 구현이면 기본으로 `ject-jds-ff`에 맡긴다. FF 스킬과 criteria는 분량이 커서 메인 맥락에 올리지 않는다. 복합 상태·폼·Portal·포커스 변경에는 사용 가능한 도구가 있으면 `ject-jds-browser`도 사용한다. 기본 동시 실행은 메인 포함 3명 이내로 제한한다. 도구가 없거나 단순한 변경이면 메인이 확인하고 독립 검토 미실행을 구분한다.

## 공통 입력과 반환

- 입력으로 저장소·branch·HEAD·dirty 범위·소유 책임·요구사항·원자료·현재 권한을 전달한다. 필요한 스킬은 저장소 안의 명시적인 파일 경로로 전달한다.
- 독립 판단이 필요하면 구현자의 결론을 정답으로 주지 않는다. 알려진 결함의 수정 확인에는 재현과 기대 결과를 전달한다.
- 반환에는 실제 읽은 코드·근거 위치·재현·기대/실제 결과·영향·실행 검사·미검증·열린 질문을 포함한다.
- 검토자는 제품 코드·baseline·의존성·설정·작업 기록 파일을 수정하거나 외부에 게시하지 않는다. 결과를 반환하면 메인이 필요한 기록을 저장한다.
- 실제 사용할 수 있는 도구를 먼저 확인한다. Bash·MCP를 운영체제 수준에서 읽기 전용으로 격리한 구성으로 간주하지 않는다.

## ject-jds-ff

[FF 검토 스킬](../../ject-jds-ff-review/SKILL.md)과 criteria 전체를 읽고 변경 용이성을 검토한다. 필요한 맥락은 [코드 리뷰](../../ject-jds-review/SKILL.md)에서 확인한다. 관련 단위별 17개 항목·실제 변경 시나리오·file:line·반증·대안 비용을 남긴다. 기능 결함·FF 의견·팀 선택을 구분하고 먼저 읽을 핵심은 세 가지 이하로 추린다. 읽지 못한 코드는 미검증으로 남긴다.

## ject-jds-browser

[브라우저 검증](../../ject-jds-browser-check/SKILL.md)과 [접근성 기준](../../ject-jds-accessibility/SKILL.md)을 읽는다. 같은 코드 상태와 요구사항을 기준으로 실제 Storybook·브라우저에서 상태·폼·키보드·포커스·시각 결과를 확인한다. 브라우저·테마·입력 방식·기대/실제·관련 기준·증거를 반환한다. 빌드·VRT·정적 검사·자동 접근성·낭독 확인을 구분하고, 없는 도구를 사용했다고 보고하지 않는다. 서버 시작은 메인이 관리하고 다른 프로세스를 종료하지 않는다.

## 도구 간 인계

Codex와 Claude Code는 같은 스킬 원본을 읽는다. 메인의 모델 설정을 이어받고 새 모델·SDK·자동 메시징을 요구하지 않는다. 다른 도구에서 재개할 때는 현재 작업 기록의 절대 경로와 요청을 전달한다. 재개한 쪽은 현재 코드와 기록을 다시 대조한다.
