# PR 작성

PR 설명을 쓰거나 고칠 때 이 문서와 [PR 템플릿](../../../../.github/PULL_REQUEST_TEMPLATE.md)을 읽는다. 초안 작성과 커밋, 푸시, PR 생성, 댓글 전송은 각각 별개의 행동이며 현재 사용자 권한을 따른다.

## 읽는 사람

리뷰어는 작업 대화를 보지 않았다. PR만 읽고 다음 질문에 답할 수 있어야 한다.

- 무엇이 바뀌었나?
- 왜 바꿨나?
- 리뷰할 때 어디를 보면 되나?
- 확인은 어디까지 했나?

이 질문과 상관없는 내용은 쓰지 않는다. 작업 순서, 시도했다가 버린 방법, 사용한 도구, 내부 평가 과정은 리뷰어가 판단하는 데 필요할 때만 한 줄로 남긴다.

## 구성

템플릿의 섹션 제목을 그대로 쓴다.

- **작업 내용**: 체크리스트 한 줄에 변경 하나를 쓴다. 리뷰어가 diff에서 확인할 수 있는 결과로 쓴다. "Kbd 테두리를 박스 안쪽에 그리도록 수정"처럼 대상과 결과가 드러나게 한다.
- **자세한 설명**: 첫 문단 한두 문장으로 무엇을 왜 바꿨는지 말한다. 이어서 변경마다 `###` 소제목을 두고, 바뀐 내용 → 이유 순으로 쓴다. diff를 줄 단위로 다시 서술하지 않는다.
- **리뷰 요구 사항**: 리뷰어의 판단이 필요한 지점만 구체적인 질문으로 쓴다. "전체적으로 봐주세요"는 쓰지 않는다.
- 선택 섹션에 쓸 내용이 없으면 비워 둔다.

전후 비교는 표로, 사용법과 구조는 코드 조각이나 트리로 보여준다. 문장으로 풀면 길어지는 내용은 대개 표 하나로 줄어든다.

## 문장

- 한 문장에 한 가지만 말한다. 두 가지면 문장을 나눈다.
- 가운뎃점(`·`)으로 명사를 셋 이상 잇지 않는다. 항목이 여러 개면 목록으로 쓰고, 각 항목은 문장으로 쓴다.
- 추상어 대신 실제 이름을 쓴다. "공개 계약을 연결했다" 대신 `TextFieldProps`, `onValueChange`처럼 리뷰어가 diff에서 찾을 수 있는 이름을 쓴다.
- "정리했다", "연결했다", "구분했다" 같은 과정 동사만으로 끝내지 않는다. 그 결과 무엇이 달라졌는지 쓴다.
- 문체는 [문체 기준](../../../../docs/ai/README.md#문체와-개선)을 따른다. 한 PR 안에서는 한 가지 문체만 쓴다.

```markdown
<!-- 고치기 전 -->

구현 지침에는 공개 API·상태 소유권·이벤트·외부 값 변경·폼·Portal·토큰·스토리·패키지 검증을 연결했어요.

<!-- 고친 후 -->

구현 단계마다 확인할 항목을 정했어요. 예를 들어 폼에 쓰는 컴포넌트는 reset한 뒤 제출되는 값까지 확인해요.
```

## 검증 결과

실행한 명령과 결과만 짧게 쓴다.

```markdown
- `npm run type-check`, `npm run lint` 통과
- Storybook에서 열린 팝업의 disabled 전환 확인
- VRT는 실행하지 않았어요. 스타일 변경이 없어요.
```

실행하지 않은 검증은 이유와 함께 한 줄로 남긴다. 캐시 사용 여부 같은 세부는 결과 해석에 영향을 줄 때만 쓴다. 실패하거나 확인하지 못한 것을 통과처럼 쓰지 않는다.

## 명세 외 합의사항

작업 중 질문·답변 기록을 현재 Figma와 디자인 문서에 다시 대조한다. 다음을 모두 만족하는 결정만 **명세 외 합의사항**으로 남긴다.

- 현재 디자인 문서에 설명되지 않았다.
- 사용자나 디자이너 같은 의사결정자가 실제로 답하거나 명시적으로 승인했다.
- 동작, 공개 API, 지원 범위, 검증 중 리뷰어가 알아야 하는 결정이다.

AI가 혼자 고른 내부 구현, 추천, 추정, 미해결 질문은 넣지 않는다. 나중에 문서에 반영된 결정은 반복하지 않고 해당 문서를 연결한다. 원문과 다르게 합의한 예외는 충돌 내용과 승인 근거를 짧게 쓴다.

리뷰 요구 사항 섹션에 소제목을 추가한다. 각 항목은 결정한 내용 한 문장으로 쓰고, 이유가 중요할 때만 짧게 덧붙인다. 근거가 필요하면 공유 가능한 Figma 노드, 문서, 스토리 링크를 단다. 개인 작업 기록의 경로는 PR에 쓰지 않는다.

아래는 형식 예시이며 실제 합의가 아니다.

```markdown
### 명세 외 합의사항

- 날짜 일부를 입력한 뒤 포커스가 이동해도 입력 내용을 유지해요. 이어서 수정할 수 있도록 정했어요.
- 팝업이 열린 상태에서 비활성화되면 닫고, 편집 중인 값을 새로 확정하지 않아요.
```

항목이 없으면 이 소제목을 생략한다. 리뷰에 영향을 주는 미결정은 열린 질문으로 따로 남기고 합의로 쓰지 않는다. 이 목록이 작업 내용이나 검증 결과를 대신하지 않는다.

## 올리기 전에

- PR만 읽은 동료가 "무엇이, 왜, 어디를 보면 되는지" 답할 수 있나?
- 설명이 최종 diff와 맞나? 작업 중에 바뀐 내용이 남아 있지 않나?
- 같은 내용을 두 번 쓰지 않았나? 디자인 문서에 있는 내용을 옮겨 적지 않았나?
- AI의 제안이나 예시를 합의처럼 쓰지 않았나?
