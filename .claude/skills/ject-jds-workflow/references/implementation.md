# 컴포넌트 구현 절차

실제 구현 요청에만 적용한다. 설계나 리뷰 요청은 요청한 산출물까지만 한다. 단순한 컴포넌트에 복합 입력의 요구를 모두 강제하지 않는다. 미결정은 임의로 채우지 않는다.

코드를 쓰기 전 [JDS 작업 지침](../../../../packages/jds/AGENTS.md)을 읽는다. 파일 이름, compound 조립, 배럴 순서, 스타일, 스토리 유틸은 그 규칙을 따른다. 타입을 선언하거나 옮기기 전에는 `docs/type-convention.md` 전체를 읽는다.

## 1. 공개 계약

기본 사용, 소비처 제어 사용, 필요한 합성 사용 예시를 먼저 쓴다. 아래 결정은 구현 전에 정한다.

| 결정           | 정할 것                                                                         |
| -------------- | ------------------------------------------------------------------------------- |
| props와 기본값 | 이름, 타입, 기본값, 허용 조합. Figma 기본 인스턴스와 문서 권장값은 다를 수 있음 |
| 값             | value, defaultValue, checked, open의 소유권과 지원하는 제어 방식                |
| 이벤트         | 발생 시점, payload, 호출 횟수, 소비처 handler와 내부 handler 순서               |
| DOM과 ref      | 실제 렌더 요소, ref 대상, HTML 속성이 전달되는 위치                             |
| 호환성         | 기존 props, 타입, export, DOM과 role, 사용처 동작 중 바뀌는 것                  |

## 2. 상태와 사건

[상태와 이벤트 계약](../../ject-jds-component-design/references/state-contracts.md)을 읽는다. 복합 컴포넌트는 실제 사건을 아래 형식으로 적고, 각 행을 스토리나 검증 시나리오로 연결한다.

| 이전 상태     | 입력이나 외부 사건        | 다음 확정값과 화면        | 이벤트                   | 포커스와 폼 결과   |
| ------------- | ------------------------- | ------------------------- | ------------------------ | ------------------ |
| 비어 있음     | 입력 시작                 | 부분 입력 보존, 확정 조건 | 호출 시점과 payload      | 선택 범위, 제출값  |
| 값 있음       | 부모가 값 변경이나 비우기 | 외부 값 반영, draft 처리  | 소비처 변경을 재통지할지 | 화면과 폼의 의미   |
| 편집 중       | 부모가 변경 거절          | 확정값과 draft의 관계     | 중복 통지 방지           | 제출값 불일치 방지 |
| 팝업 열림     | disabled, readOnly 전환   | 값 변경 방지, 닫힘 정책   | 늦은 콜백 처리           | 포커스의 대안      |
| 초기값 변경됨 | form reset이나 취소       | 제어 방식별 초기화        | reset 통지 정책          | 실제 FormData      |

## 3. 화면과 콘텐츠

Figma 레이어 구조를 DOM으로 그대로 옮기지 않는다. HTML 의미와 키보드 동작에 맞게 구성하고, hover, active, focus-visible은 실제 상호작용에 연결한다. 장식 레이어가 포인터 입력이나 접근성 트리를 막지 않는지, focus ring이 잘리지 않는지 본다.

긴 레이블과 오류, 빈 콘텐츠, 조건부 ReactNode, 다국어 길이, 좁은 화면과 확대에서 확인한다. `false`, `null`, `0`, 빈 문자열의 렌더링 의미는 prop 계약으로 정한다. 쓰지 않는 래퍼의 간격이 남는지도 본다.

## 4. 구현 단위와 FF

컴포넌트, 훅, 유틸, 주요 내부 함수, 모듈 상수 맵을 검토 단위로 적는다. 공통화는 사용처의 동작과 변경 이유가 같을 때만 한다. 구현하면서 새 상태 추가, 값 형식 변경, 특정 사용처만 동작 변경 같은 시나리오로 수정 범위를 따져 본다. 코드 줄 수나 조건문 개수를 결함 기준으로 삼지 않고, 메모이제이션과 Context 분리는 실제 측정 근거가 있을 때만 한다.

구현을 마치면 검토 단위 목록, 요구사항, 변경 범위(기준 브랜치와 커밋하지 않은 변경 포함)를 `ject-jds-ff` 역할에 넘긴다([역할과 반환 계약](roles.md)). 메인은 FF 스킬을 읽지 않는다. 돌아온 지적 중 반영할 것을 고치고, 고친 범위만 다시 맡긴다.

## 5. 스토리

스토리는 API 사용 문서이자 실행 가능한 시나리오다. 기본 사용에 더해 2번 표에서 위험한 사건을 고른다. 모든 조합 대신 핵심 상태와 충돌하기 쉬운 조합을 고르고 이유를 남긴다. assertion은 로직의 결과를 확인하고, 내부 구현을 그대로 따라 쓰지 않는다.

기존 Storybook 테스트와 브라우저 도구로 먼저 실행한다. 실행할 수 없으면 새 패키지를 설치하지 않고 확인하지 못한 범위와 필요한 도구를 적는다. 결과는 [검증 판정](quality-gates.md#결과와-완료-범위)대로 기록한다. 배포 코드가 바뀌면 [패키지 검사](../../ject-jds-package-check/SKILL.md)와 체인지셋 규약을 따른다.
