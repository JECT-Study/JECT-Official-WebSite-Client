# 컴포넌트 구현 절차

설계·리뷰 요청에는 승인된 산출물까지만 진행한다. 실제 구현 요청을 받았을 때 아래 순서와 해당 검증을 적용한다. 단순한 컴포넌트에 복합 입력의 모든 요구를 강제하지 않는다.

요구사항 초안의 확인된 사실·제안·미결정을 구분하고 확정된 요구를 코드·스토리·검증 시나리오에 연결한다. 의존하는 사용자 결정이 없으면 진행하고, 미결정은 임의로 채우지 않는다.

## 1. 소비처와 공개 계약

기본 사용, 소비처 제어 사용, 필요한 합성 사용 예시를 먼저 작성한다. 명세를 만족하는 가장 작은 API를 선택한다. 컴포넌트가 보장하는 동작과 소비처의 서비스 검증·비동기 요청·메시지 작성 책임을 나눈다.

| 결정           | 반드시 설명할 것                                                                            |
| -------------- | ------------------------------------------------------------------------------------------- |
| props와 기본값 | 이름·타입·기본값·허용 조합·기본 사용. Figma 기본 인스턴스와 문서 권장값을 구분              |
| 값             | value/defaultValue/checked/open의 소유권과 지원하는 제어 방식                               |
| 이벤트         | 발생 시점, payload, 호출 횟수, 소비처 handler와 내부 handler 순서, preventDefault 존중 여부 |
| DOM·ref        | 실제 렌더 요소, ref가 가리키는 대상, HTML 속성이 전달되는 위치                              |
| 합성           | 단일/compound/slot/편의 API의 필요성과 소비처 책임. Context 도입 이유                       |
| 호환성         | 기존 props·타입·export·DOM/role·사용처 동작 중 바뀌는 것                                    |

코드를 쓰기 전 [JDS 작업 지침](../../../../packages/jds/AGENTS.md)을 읽는다. 파일 이름·compound 조립·배럴 순서·스타일·스토리 유틸은 그 규칙을 따른다. 타입을 선언·이동하기 전 현재 `docs/type-convention.md` 전체를 읽는다. 불가능한 조합은 적절한 유니온으로 제한하되 일반적인 사용을 복잡하게 만들지 않는다. 공개 타입과 API는 배럴에서 사용할 수 있어야 한다.

## 2. 상태와 사건의 순서

[상태·이벤트 계약](../../ject-jds-component-design/references/state-contracts.md)을 읽는다. 입력의 화면 draft, 확정값, 표시 문자열, 제출값이 다르면 각각의 의미와 변환·실패 정책을 정의한다. 꼭 필요한 상태만 보관하고 파생 가능한 값과 구분한다.

복합 컴포넌트에는 다음 형식으로 실제 사건을 적는다.

| 이전 상태     | 입력/외부 사건           | 다음 확정값·화면            | 이벤트                   | 포커스·폼 결과      |
| ------------- | ------------------------ | --------------------------- | ------------------------ | ------------------- |
| 비어 있음     | 입력 시작                | 부분 입력 보존·확정 조건    | 호출 시점과 payload      | 선택 범위·제출값    |
| 값 있음       | 부모가 값 변경/비우기    | 외부 확정값 반영·draft 처리 | 소비처 변경을 재통지할지 | 화면·폼의 의미 일치 |
| 편집 중       | 부모가 변경 요청 거절    | 확정값과 draft의 관계       | 중복 통지 방지           | 제출값 불일치 방지  |
| 팝업 열림     | disabled/readOnly로 전환 | 값 변경 방지·닫힘 정책      | 늦은 콜백 처리           | 포커스의 대안       |
| 초기값 변경됨 | form reset/취소          | 제어 방식별 초기화          | reset 통지 정책          | 실제 FormData       |

입력 수단은 키보드·붙여넣기·IME·포인터·모바일 중 관련 경로를 포함한다. 기간 제한·선택 불가 조건을 팝업과 직접 입력 중 어디에 적용하는지 명시한다. `defaultValue`를 초기값과 reset 기준 중 어떻게 사용하는지도 정한다.

타이머·리스너·비동기 작업은 대상 교체와 unmount에서 정리한다. 이미 열린 Portal, 종료 애니메이션, 예약된 callback이 비활성 전환 후 값을 바꾸는지 확인한다. 오래된 결과 무시와 실제 취소는 구분한다.

## 3. 기존 primitive와 접근성

현재 native 요소 → Radix/JDS primitive → wrapper → 소비처 경로를 읽는다. Field의 레이블/설명 연결, 공통 focus/state 훅, Listbox 등의 책임을 다시 구현하기 전에 재사용 가능성을 확인한다. primitive가 보장하는 동작도 wrapper의 prop/event/style 조합 후 유지되는지 검증한다.

관련 키보드 표, 진입·이탈·복귀 포커스, 이름/설명/상태, 폼 제출/초기화 계약을 구현과 함께 작성한다. disabled/readOnly/required/invalid의 표시와 실제 HTML·ARIA 의미가 일치해야 한다. Portal은 DOM 경계가 달라 부모 fieldset만으로 비활성 정책이 전달된다고 가정하지 않는다.

## 4. 토큰과 레이아웃

[토큰 스킬](../../ject-jds-tokens/SKILL.md)로 현재 입력 → 생성기 → vanilla-extract 소비 경로와 의미를 확인한다. 동일한 raw 값만 보고 토큰을 대체하지 않는다. semantic intent, light/dark, state와 조합을 확인한다. 현재 JDS의 컴포넌트 토큰 미사용 결정을 임의로 바꾸지 않는다. `vars`·`recipe`·`createVar`·타이포 유틸과 pseudo-element 할당은 [JDS 작업 지침](../../../../packages/jds/AGENTS.md#스타일-vanilla-extract)을 따른다.

Figma 레이어 구조는 디자인 관리 구조다. HTML 의미·키보드 동작·레이아웃 요구에 맞게 DOM을 구성한다. hover/active/focus-visible은 실제 상호작용과 연결한다. 장식 레이어가 포인터 입력과 접근성 트리를 방해하지 않는지, focus ring이 잘리지 않는지 확인한다.

긴 레이블·오류·빈 콘텐츠·조건부 ReactNode·다국어 길이, 좁은 화면·확대에서 확인한다. `false`, `null`, `0`, 빈 문자열의 렌더링 의미는 해당 prop 계약을 기준으로 결정한다. 사용하지 않는 래퍼의 간격이 남는지도 본다.

## 5. 구현 단위와 FF

컴포넌트·훅·유틸·내부 주요 함수·모듈 상수 맵을 검토 단위로 기록한다. state/event/style 책임을 따라 코드를 배치한다. 공통화는 실제 사용처의 동작과 변경 이유가 같을 때 선택하고, 갈라질 요구가 있으면 독립성을 유지하는 비용과 비교한다.

구현 완료 전 [FF 스킬](../../ject-jds-ff-review/SKILL.md)과 [17개 항목](../../ject-jds-ff-review/references/criteria.md) 전체로 각 단위의 17개 항목을 검토한다. 새 상태 추가, 값 형식 변경, 특정 사용처만 동작 변경 같은 현실적인 시나리오로 수정 범위를 추적한다. 코드 줄 수·조건문 개수·함수 길이를 결함 판정 기준으로 사용하지 않는다. 메모이제이션·Context 분리는 실제 렌더/구독/번들 근거가 있을 때 판단한다.

## 6. 스토리와 검증

스토리는 API 사용 문서와 실행 가능한 시나리오다. 기본 사용에 더해 관련된 controlled/폼/레이블 없는 사용/상태 전환/경계값/Portal 조합을 만든다. 모든 Cartesian 조합 대신 핵심 상태와 충돌 위험 조합을 선택하고 선택 근거를 남긴다. 로직의 결과를 확인하는 assertion을 사용하고 내부 구현을 그대로 따라 쓰는 검사는 피한다. 레이아웃은 `@storybook-utils`를 쓰고, VRT 베이스라인은 로컬에서 만들지 않는다([JDS 작업 지침](../../../../packages/jds/AGENTS.md#스토리)).

기존 Storybook 테스트·브라우저 도구로 먼저 실행한다. play 코드 존재·스토리 빌드·VRT 캡처·play assertion 실행은 서로 다른 결과다. 실제 실행이 불가능하면 새 패키지를 임의로 설치하지 않고 해당 미검증과 필요한 도구를 기록한다.

현재 AGENTS의 type-check/lint를 실행하고 관련 Storybook/패키지/시각 검증을 적용한다. 커밋 전 format 규칙을 따른다. 이번 범위 밖 변경이 나오면 원인과 소유권부터 확인하며 다른 작업을 되돌리지 않는다.

## 7. 소비처와 변경 안내

공개 배럴, 타입, 지원 React 범위, ESM/CJS, CSS 진입점, 필요한 provider와 ref·event 동작을 실제 패키지 기준으로 확인한다. 빌드 시스템을 바꾸거나 Next/RSC 호환성을 약속한다면 해당 소비 환경의 실행 근거가 필요하다.

배포 코드가 바뀌면 현재 changeset-guide 전체를 읽고 소비처 영향과 migration을 작성한다. 스토리·문서만 바뀐 작업과 배포 변경을 구분한다. 미해결 질문이나 필수 동작 미검증이 있으면 전체 구현 완료를 주장하지 않는다.

PR 설명이 필요하면 [명세 외 합의사항](pull-request.md)을 적용한다. 구현 중 정한 모든 내부 선택이 합의사항은 아니다.
